# apps/ —— 作业录入 + 大屏宠物选题闭环

对应 PRD 模块二（FR-HW-\*）、模块三（FR-PET-\* / FR-VOTE-\*）与 DESIGN §3.4、§5、§9。

```
apps/
  api/       FastAPI + SQLAlchemy 后端(含 26 条回归测试)
  screen/    教室大屏(学生端,免构建原生页面)
  teacher/   教师控制台:作业录入 / 讲评看板 / 学生与宠物
```

## 教师端三个页签

| 页签 | 做什么 |
| --- | --- |
| **作业录入** | 新建作业 → **拍照识别**或粘贴文本切题 → 自动挂知识点候选 → 逐题校对 → 发布到大屏 |
| **讲评看板** | 开窗/关窗、实时聚合（人数 × 归因权重排序）、点行展开学生名单 |
| **学生与宠物** | 全班宠物花名册、能量与提交次数、从未提交名单 |

## 运行

```bash
cd apps/api && pip install -r requirements.txt
```

配置 LLM（不配也能跑，只是没有照片识别）：

```bash
cp .env.example .env
```

填入 `MATHMATE_LLM_API_KEY` 等三项后，验证连通性：

```bash
python scripts/llm_smoke.py
```

VS Code / Cursor 用户直接按 **F5**，`.vscode/launch.json` 里已配好九个调试入口。

```bash
cd apps/api && python -m app.seed
```

```bash
cd apps/api && python -m uvicorn app.main:app --reload --port 8000
```

| 入口 | 地址 |
| --- | --- |
| 教师控制台 | http://localhost:8000/teacher/ |
| 教室大屏 | http://localhost:8000/screen/ |
| API 文档 | http://localhost:8000/docs |

## 日志

```bash
MATHMATE_LOG_LEVEL=DEBUG MATHMATE_LOG_FILE=logs/api.log python -m uvicorn app.main:app --port 55101
```

配置在 `app/logging_conf.py`。此前**完全没配**：模块里写了 `log.warning`
但根 logger 没有 handler，于是识别失败时服务端一行都不打，只能靠接口返回的
那句话猜——排查那张 7.8MB 照片就吃了这个亏。

一次照片录入现在留下这些（`[9872aa99]` 是请求 id，串起同一次调用）：

```
上传 hw.jpg → fd52df2d….jpg  7.8MB  作业=今日作业(27c3945e…)  识别=True 覆盖=False
识别预处理 src_bytes=8187299 src_size=5712×4284 exif_orientation=6
           out_size=1800×2400 prepared=True out_bytes=866465 quality=85
[9872aa99] → …/chat/completions model=my-combo 消息1条 载荷1129.4KB max_tokens=6000
[9872aa99] ← 200 10.9s 返回2346字 tokens=337974→803
照片识别成功 11.4s,得到 8 道题
```

两个细节：

- **落盘文件名进日志**，出问题能凭 `/uploads/<name>` 直接找到原图复现
- **`sk-` 开头的长串在写出前打码**（`_RedactKey`）。正常路径不会记密钥，
  这层挡的是「某天有人顺手 log 了整个 headers」，而日志经常被贴进工单

### 报错分两路

原始网关 JSON 只进日志，界面上给教师能据以行动的一句话（`LLMUnavailable.hint`）。
判定**先看响应体再看状态码**——同一个 400 可能是「图太大」也可能是「模型名不对」，
一个该改照片、一个该改配置；这个网关对未知模型名返回的正是 400 而非 404，
只按状态码给提示会把配置错误说成「稍后重试」，而重试一万次也不会好。

## 照片识别（FR-HW-04/05）

`app/llm.py` → `recognize_problems()`。多模态模型直接读作业照片，输出题号、题型、
题干（数学式转 LaTeX）、选项、难度、是否含几何图形。多页作业逐张上传依次追加。

三条硬约束写在代码里，不靠提示词：

- **识别结果一律 `review_status="auto"`**，未逐题校对无法发布（FR-HW-11）。
  模型识别得再好也不例外 —— 数学题一个符号错就毁掉整道题。
- **原图始终保存**，无论识别成功与否。识别失败时原图就是唯一的降级依据。
- **任何失败都降级为 200 + 说明**，不抛 5xx。超时、限流、返回垃圾，
  教师的录入流程都不能被模型中断（NFR-AV-07）。

看不清的字模型会用 `⬚` 占位而不是猜测填补；含几何图形的题会计入 `with_figure`
提示教师 —— 图形本身无法被文本还原，这类题必须对照原图校对。

### 发送前必须预处理（`llm.prepare_image`）

**网关对单张图片有 1 MiB 硬限制**，而手机拍的作业照普遍 5–10 MB，直接发过去
稳定吃 `400 Image input is too large`。上传上限 24MB 只管**留存**——原图是
识别失败时教师唯一的降级依据，不该因为大而被拒收；送给模型的是压缩过的副本。

| 处理 | 为什么 |
| --- | --- |
| 长边缩到 2400px、JPEG q85，超预算则先降边长再降画质 | 实测 2400px 比 1600px 又快又准（28s vs 48s，长题干不被截断）；作业题的关键是笔画清晰，分辨率比压缩率值钱 |
| 套用 EXIF 方向 | 手机横竖拍靠 EXIF 标记，原始像素常是躺着的。不摆正的话教师在浏览器里看到的是正的、模型看到的是歪的 |
| 不是图片/损坏时原样放行 | 预处理不该中断上传流程 |

一张 5712×4284 / 7.8MB 的真实作业页，预处理后 1800×2400 / 0.85MB，识别出 8 道题。

## 知识点标注

`app/kg_index.py`（检索）+ `app/llm.py` → `rerank_kp()`（可选重排）。
**只在 L1 母版的 141 个知识点里做选择，永不发明新知识点**（DESIGN §5）。

这条约束由**结构**保证而非提示词：候选恒由检索产生，LLM 只返回候选里的 id，
越界的返回值在 `llm.rerank_kp` 和 `authoring._annotate_batch` 两处各拦一次。
编一个「二次函数的对称轴性质」这种听起来很对但不在母版里的知识点，
会污染整个图谱统计。

检索部分三路证据加权：

1. **词根命中** — 题干里原样出现「分式」「一次函数」这类考点词根
2. **术语相似** — 与知识点画像（名称 ×3 + 描述 + 章节）的字符二元组相似度
3. **近邻投票** — 与 288 道**已标注真题**的相似度检索，用邻居标签投票

公式结构（`\frac` / `\angle` / `\odot` …）会被抽成带 `zz` 前缀的伪词，只参与题目之间的比对，**不冒充知识点名称**——早期版本把 `\frac` 直译成「分式」，结果一道问「哪个是分式」的题反被一堆含分数线的实数题带偏。

### 实测:LLM 重排并不比检索更准，所以默认关掉了

288 道已标注真题上的留一法对比（`python scripts/llm_eval_kp.py --n 0`，会真实计费）：

| 指标 | 检索 | 检索 + LLM 重排 |
| --- | --- | --- |
| top-1（全体 287 题） | **47.7%** | 42.2% |
| 章节 top-1（全体） | **63.4%** | 61.0% |
| top-1（只看模型愿作答的 240 题） | 52.1% | 50.4% |
| 〔天花板〕金标落在 top-8 候选内 | **72.1%** | — |

Wilson 95% 区间在同一子集上几乎完全重叠（45.8–58.3% vs 44.1–56.7%），
即**测不出差异**。模型在 16% 的题上弃权（其中 12 道检索本可答对），
纠正了 33 道、带偏了 37 道，基本相抵。

所以 `MATHMATE_LLM_RERANK_KP` **默认为 0**：花钱、变慢、没有可测得的收益，
三者同时成立时不应该默认开启。真正的瓶颈是**检索召回**——
金标压根不在 top-8 候选里的占 28%，重排再聪明也够不着。

两点诚实的保留：

- 金标本身有噪声。例如「一个凸多边形剪去一个角后内角和是 2520°」，
  语料标的是「三角形的内角和与外角」，模型选的「多边形的内角和与外角和」
  明显更对，却被算作「带偏」。这类噪声会低估重排，但「基准不准」
  正是让坏改动蒙混过关的常用借口，所以只作为注记，不作为开启的理由。
- 教师在校对页单题点 **「✨ AI 重推」** 不受此开关影响，且实测有用：
  上面那道分式题检索给的是「分式的运算」，点一下改成「分式的概念与基本性质」，
  并给出理由「考查分式的识别，属概念题」。人主动求助、结果当场可判，
  与批量默认自动跑是两回事。

检索基线单独复现（不打网络、不计费）：`cd apps/api && python -m app.kg_index --eval`

命中按**标签集合**判定（同一道题可能合法归属多个知识点）。

**这仍然是候选推荐，不是自动标注。** PRD FR-HW-07 的目标是 ≥90%，差距明显。
瓶颈是标注语料只有 288 条、覆盖 141 个知识点中的 69 个；典型失败是题干几乎全是公式、
没有中文关键词的题（如「计算 √12−√3」）。提升路径是补语料以抬高召回天花板，
而不是换更强的重排模型。教师逐题校对是强制闸门，正是为此存在。

## 宠物形象（FR-PET-01）

24 种萌宠，素材是 **Noto Animated Emoji**（Google，**CC BY 4.0**），
由 `python scripts/fetch_pets.py` 下载并规格化到 `apps/shared/pets/`。

```bash
python scripts/fetch_pets.py
```

| 产物 | 用途 | 体积 |
| --- | --- | --- |
| `<name>.png` 256×256 | 大屏网格 / 教师花名册 | 24 个共 822 KB |
| `<name>.webp` 256×256 动图 | 只在宠物被点中放大时加载 | 24 个共 6.0 MB |

**为什么分两级**：网格里 40 只同屏，全用动图既吵又费电，还要一次拉 6 MB；
全用静态又少了「宠物」该有的活气。所以网格用静态帧，学生点中自己那只时
才换成动图——宠物在被认领的瞬间活过来，正好是该有反馈的那一刻。
`petSVG(species, hue, { alive: true })` 控制。

规格化在**生成期**做掉了两件事，运行期因此不需要每物种一组魔法偏移量：

- 按内容自动裁边、统一底部对齐到画布 248/256 处，与 `pet.js` 里的影子对齐
- 抽帧到 15fps（原图多是 30fps、上百帧），素材总量从 12 MB 降到 6 MB

两个坑值得记：

- **逐帧裁边会抹平动作。** 最初 `normalize()` 每帧各裁各的，结果兔子跳起来的位移
  变成原地不动，而且帧间差分压缩失效（325 KB vs 并集法 304 KB）。必须用整段动画的
  **并集包围盒**算一次变换再套到每一帧。
- **抽帧后要把时长按组求和。** 只写 `durations[::step]` 会让 Pillow 那条路快一倍，
  而 ffmpeg 那条路由 `-framerate` 定速不受影响 —— 于是「播放速度取决于哪个编码器
  体积更小」。脚本现在会逐个核对生成动图的循环总时长与原图之差，超过 5% 就报警并
  以非零码退出。

核对时长这件事本身也踩过一次：`Image.seek()` 之后不调 `load()`，Pillow 读到的
`info["duration"]` 是默认值 40ms 而不是真实值，害我拿假读数追了一个不存在的倍速 bug。
`loop_ms()` 里那句 `im.load()` 不能省。

**署名是硬性要求**：CC BY 4.0 规定必须署名，且要出现在素材实际露面的地方。
署名在教师端「学生与宠物」页宠物墙下方 + `apps/shared/pets/CREDITS.md`。

上一版素材（Microsoft Fluent Emoji 3D，MIT，无需署名）保留在
`apps/shared/pets-fluent3d/`。换回去改 `pet.js` 的 `SPECIES_ZH` 与 `seed.py` 的
`SPECIES` 即可；当初换掉是因为它是侧身写实像，40 只挤在网格里学生认不出自己那只。

## 与设计文档的三处偏离

首个切片的刻意取舍，都不是疏忽：

| 项 | DESIGN 规划 | 当前实现 | 影响 |
| --- | --- | --- | --- |
| 数据库 | PostgreSQL + pgvector + RLS | SQLite | 零配置可跑；schema 保持 PG 兼容（字符串 UUID、JSON 代替 ARRAY）。**RLS 租户隔离未实现** |
| 大屏 | React + Vite + PixiJS | 原生 ES 模块 | 免构建、便于逐条验证；API 契约已固定，迁移是机械工作 |
| 模型编排 | 版面分析 / 公式识别 / 知识点标注分别调用 | 单次多模态调用完成前两项 | 一页作业一次调用（约 15–30s），少一次往返；知识点仍走本地检索 |

未配 `MATHMATE_LLM_API_KEY` 时自动退回 **NFR-AV-07 降级路径**（仅切题 + 教师手动录入，
不阻断主流程），上传原图明确返回 `recognition.status = "unavailable"`，
界面上也会换成「上传原图（仅留存）」——**不假装识别成功**。

## 已实现的约束

这些是 PRD 里标注「不可妥协」的规则，均有测试覆盖：

- **大屏 bootstrap 不下发学生姓名**（FR-VOTE-10）—— 姓名会把「我不会」变成公开信号
- **选题上限服务端强制**（FR-VOTE-04）—— 只靠前端拦不住手机端/脚本
- **归因限定七类枚举**（PRD §3.3.3）—— 自由文本无法聚合
- **未发布的作业不能开窗**（FR-HW-11）—— 未经教师校对不得推给学生
- **能量与答对率无关，且重投不重复发放**（FR-PET-05）—— 否则弱生宠物永远长不大
- **幂等 + 乱序补传**（NFR-AV-03）—— 离线队列会重复、会乱序
- **断网可完整投票**（NFR-AV-02）—— 提交先落 IndexedDB，恢复后自动补传
- **主导归因按「人数 × 归因权重」**（DESIGN §7.1）—— 3 个「完全没思路」压过 5 个「粗心」
- **未逐题校对不能发布**（FR-HW-11）—— 发布接口硬拦，返回 409 与待校对题号
- **知识点只能选自 L1 母版**（DESIGN §5）—— 教师手选非法 id 返回 422
- **已发布的作业冻结**（改题会让题面与已投的票对不上）—— 需先撤回，投票中不允许撤回
- **题号连续无空洞**（大屏上是学生的定位锚点）—— 删题后两阶段重排，避开唯一约束；
  识别时丢掉空题也按剩下的重编号，不留洞
- **宠物花名册不做能量排行**（FR-PET-06）—— 按座位号排序；公开排行榜会变成对倒数学生的羞辱
- **模型不得发明知识点**（DESIGN §5）—— 候选集外的 `kp_id` 两处各拦一次，退回检索结果
- **模型说「候选都不对」时清空标注**而不是硬塞一个 —— 空标注会标黄逼教师手选，
  错标注则可能被顺手确认
- **LLM 失败一律降级为 200 + 说明**（NFR-AV-07）—— 超时/限流/返回垃圾都不能中断录入
- **降级必须让教师看见** —— 悄悄退回检索结果比不降级更糟
